## 2. Module-by-Module Resolutions

### 2.1 Better Auth boundary

- `user`, `session`, `account`, `verification` are **owned and generated by Better Auth** (via `@better-auth/cli generate`). This spec mirrors their shape for FK-typing purposes only — never hand-edit `db/schema/auth.ts` independently of what Better Auth actually generates for your enabled plugins (email/password, Google, username).
- The **username plugin** adds `username`/`displayUsername` directly to Better Auth's `user` table. This resolves Module 2 Q1: `name` and `username` live on Better Auth's `user`, **not** duplicated onto `application_profile`.
- Every SkillTrail table's `user_id` is a `text` FK to `user.id` (Better Auth uses text/nanoid IDs by default, not UUID).

### 2.2 Application Profile

- `application_profile` is 1:1 with `user` (own PK = FK to `user.id`), holding only SkillTrail-specific personalization: `experienceLevel`, `preferredPlatforms`, structured writing prefs, free-form writing instruction.
- **Technologies/interests → normalized catalog + junction**, not JSONB arrays. Reasoning: these have real relational value — a shared, growing, de-duplicated suggestion list across users, autocomplete queries, and potential future use in discovery personalization matching. That's independent lifecycle + reuse, which earns a table per principle 4.1.
- **Custom and suggested values share one table** (`technology`, `interest`), distinguished by `isCustom` + `createdByUserId`. When a user types a custom technology, it's inserted once (unique on lowercased name) and becomes available as a suggestion to everyone afterward. This directly resolves Module 2 Q3 and is a deliberate product-shaping decision — **[ASSUMPTION]**: confirm you're fine with custom entries becoming globally visible suggestions rather than staying private to the user who typed them.
- **Preferred platforms stay a plain enum array column**, not normalized — only two possible values in V1, no independent lifecycle. Matches principle 4.4.
- **Writing preferences are structured columns, not JSONB** — `writingTone`, `technicalDepth`, `emojiUsage` enums + `writingInstruction` free text. Structured columns give the AI abstraction layer typed, validated input; JSONB would just move validation into application code for no benefit at this fixed shape. **[ASSUMPTION]** — the enum value sets themselves (e.g. `casual | balanced | formal`) aren't specified anywhere upstream; I picked reasonable defaults. Confirm/adjust the actual label sets before shipping onboarding copy.

### 2.3 Social Connections

- `status` enum: `connected | disconnected | expired | revoked`. User disconnect is `disconnected`. Token expiry is `expired`. Platform-side revocation is `revoked`. There is **no** separate health enum or `health` / `health_detail` columns. Reconnect restores `connected`.
- Unique identity is **global and final**: `UNIQUE(platform, platform_user_id)`. That is the external-identity ownership constraint. `(user_id, platform)` is a non-unique lookup index only; a user may have multiple accounts on the same platform.
- `platformCapabilities` is JSONB, not typed columns. LinkedIn and X capability data don't overlap at all (X: premium tier → char limit; LinkedIn: org admin rights) — a shared typed-column table would be mostly-null for every row. JSONB here isn't "not knowing the schema," it's the schema genuinely being platform-divergent.
- Disconnecting an account **does not cascade to Publications.** A publish attempt against a disconnected connection fails naturally at Trigger.dev execution time into `publish_failed` with `failureReason = 'account_disconnected'` — no FK-level cascade needed, this is pure application logic hitting a normal status check.
- Deleting the *remembered* connection (not just disconnecting) sets `publication.social_connection_id` to `NULL` via `ON DELETE SET NULL` — history is preserved (text, external post ID/URL are already denormalized onto `publication` itself), only the live link to the connection row is dropped.

### 2.4 Content

- `origin` enum (`manual | research | discovery`) + nullable `research_id` / `discovery_item_id` FKs makes origin explicit and queryable, rather than inferring it from which FK happens to be non-null.
- **[ASSUMPTION]** — added `processingStatus` (`raw | analyzing | understood | failed`) to `content`. Nothing upstream assigns a table to the PRD's "RAW_INPUT → ANALYZING → ANGLES_GENERATED" pipeline stages; those states describe the *whole* pipeline (content understanding → angle generation → drafting → publishing), and each stage's state already lives somewhere specific once you have Angle/Draft/Publication tables. The only stage without a natural home is "is the AI still digesting this Content item," so that's what `processingStatus` tracks — nothing more.
- `understandingResult` (JSONB) caches the AI's extracted problem/approach/solution/challenges/learning breakdown on `content` itself, **not** as an `ai_generation` row — AI review/accept/reject/undo is explicitly locked to Draft-level only (Engineering Spec §7). Content understanding is regenerable supporting data, not a reviewable proposal.
- One `content` row references **at most one** `research_id` (not many). If this needs to change later (combining multiple research sessions into one content item), it's a straightforward migration — not worth the complexity now for a case the PRD never asked for.

### 2.5 Angle

- **Shared between Content and Research** via two nullable FKs (`content_id`, `research_id`) + a CHECK constraint enforcing exactly one is set. This is what makes "Research → Content → Composition, angle carries over" work without duplicating angle rows when research becomes content.
- No `source` column — every angle row is AI-generated by construction. A composition with no angle simply has `angle_id = NULL`; there's no "manual angle" entity because nothing upstream describes a user hand-authoring an angle.

### 2.6 Composition / Draft

- **`draft` is a single row per `(composition_id, platform)`, enforced by a unique constraint — never versioned as multiple rows, no `archived` status.** All history lives in `ai_generation`. This directly resolves "what constitutes an active draft / do we allow archived drafts" by making the question not apply: there's exactly one draft, full stop, mutated in place.
- `aiAssisted` boolean (not an enum) tracks whether AI has ever touched this draft — simpler than modeling "source" as a static enum when a manual draft can become AI-assisted mid-life and the interesting fact is just "has AI ever been involved," for cost/usage-tracking purposes.
- `pendingAiGenerationId` / `currentAiGenerationId` (both nullable FK → `ai_generation.id`) are the mechanism for "proposal survives refresh," "manual editing blocked while pending," and "show current accepted version" — no separate proposal-state table needed.

### 2.7 X-specific model

- `draft.xPostType` enum (`standalone | reply | self_reply | thread | quote`), nullable, populated only when `platform = 'x'`.
- **Reply and quote targets can point at either an external post (fetched via the picker, cached in `x_external_post`) or a past SkillTrail `publication`.** One pair of nullable FK columns (`targetExternalPostId`, `targetPublicationId`) on `draft` covers both reply and quote, since a draft is exactly one `xPostType` at a time — the meaning of "target" is disambiguated by `xPostType`, not by having four separate FK pairs.
- `x_thread_post` holds one row per thread item (`position`, `bodyText`), only present when `xPostType = 'thread'`. Unique on `(draft_id, position)`.
- `x_external_post` is a **lightweight cache**, not a Publication — resolves "how are external posts represented without pretending they're local Publications." Unique on `(social_connection_id, platform_post_id)`.
- `ai_generation.target_x_thread_post_id` (nullable) scopes an AI operation to a single thread item vs. the whole draft, which is how "regenerate one thread post" vs. "regenerate entire thread" are distinguished without two separate history tables.

### 2.8 Media

- **One `media` table** with a `kind` discriminator (`image | document`), not two tables — the metadata overlap (storage key, filename, mime, size) is high enough that splitting would just duplicate columns for a `width`/`height` pair that's null half the time either way.
- `content_context_media` and `draft_media` are separate junction tables (not one generic "media_usage" table) because they genuinely have different shapes: context attachments don't need ordering, publishing media does (`position`), and publishing media can additionally scope to a specific `x_thread_post_id`.
- **Deleting a `media` row is `RESTRICT`ed while it's referenced anywhere** (context or publishing) — a user must explicitly detach it first. This prevents silently breaking a scheduled snapshot's media reference.
- Same media asset **cannot appear twice** in one draft or one thread-post (enforced via partial unique indexes on `draft_media`) — no product requirement calls for duplicate attachments, and disallowing it keeps ordering unambiguous.

### 2.9 Publication / Scheduling

- `publication.composition_id` is `ON DELETE RESTRICT` — this is the enforcement point for "Content deletion must not silently destroy publication history" (see §2.4). `publication.draft_id` is nullable + `SET NULL`, kept only for UI traceability ("created from this draft"), never read as the source of truth for what was actually published.
- **Snapshot is JSONB**, not normalized rows. It needs to freeze text + media refs/order + thread structure + reply/quote targets + platform settings as one atomic, immutable, easy-to-diff blob — normalizing it would mean maintaining a full parallel "frozen" schema of every mutable table it might reference. This is a deliberate, scoped exception to "no polymorphic FKs" (the JSONB isn't a foreign key relationship at all — it's an opaque historical payload, never joined against).
- `failureReason` enum (`account_disconnected | platform_error | rate_limited | validation_error | unknown`) makes `publish_failed`/`delete_failed` machine-readable without inventing a full error-taxonomy table.
- Cancelled/deleted publications are **retained forever**, never purged — this is the historical record the "publication history" P0 feature is built on, and V1 volume (~10 users) makes retention cost irrelevant.
- `userId` is denormalized directly onto `publication` (not derived by joining through composition→content) — this is one of the few tables where a direct `user_id` earns its keep per Module 18's own rule, since the dashboard's primary queries are literally "this user's publications by status" and "publications due to run by scheduled time," both of which need a flat, indexable `user_id`.

### 2.10 AI Generation

- **One table**, no separate proposal/state table. `status` (`pending | accepted | rejected | failed`) plus the two pointer columns on `draft` (§2.6) cover the entire review/undo/compare/restore/history lifecycle from Engineering Spec §7.
- Only `beforeText`/`afterText` are stored (no generic `diffFields` JSONB) — V1's only AI-mutable field is text (media is user-attached, never AI-modified), so a generic multi-field diff structure would be unused complexity.
- **Restore creates a new `ai_generation` row** (`operation = 'restore'`, `status = 'accepted'` immediately, since restore already requires explicit user confirmation before it happens) rather than mutating the historical row being restored from. This satisfies "restoring does not delete newer history" for free — nothing is ever deleted or rewritten, only appended.
- `operation` enum: `generate_draft | edit_draft | regenerate | restore`. Content-level operations (`understandContent`, `generateAngles`) are **not** `ai_generation` rows — they populate `content.understandingResult` and create `angle` rows directly, since draft-level review semantics (accept/reject/undo) don't apply to them.

### 2.11 Research

- `research` is its own session/attempt record; there's no separate "execution" concept — a failed research attempt just sets `status = 'failed'`, and the user retries by creating a new `research` row (simpler than modeling attempts-within-a-session for V1 volume).
- `research_source` is a genuine child table (not JSONB) because sources have their own reasonable fields (`url`, `title`, `snippet`, `fetchedAt`) and the AI-safety requirement ("retain source information so the user can verify claims," Engineering Spec §25/27) benefits from being able to query/display them independently.
- `triggerTaskId` nullable text — populated only when research actually runs through Trigger.dev (long-running/multi-source/retry-prone); fast synchronous research leaves it null.

### 2.12 Discovery / Personalization

- `discovery_item.category` is **plain indexed text, not a Postgres enum** — the PRD explicitly states categories "evolve based on user behavior," which a fixed enum can't do without a migration every time a new category emerges.
- `discovery_item.externalKey` (unique) is the global-dedup mechanism — a normalized source URL or content hash, decided at ingestion time by the Trigger.dev background job.
- **`suggestedAngles` is a plain `text[]` column on `discovery_item`, not a reuse of the `angle` table.** This is the one place I deliberately did *not* reuse Angle, and the reasoning matters: discovery-item angle suggestions are global, display-only bullet strings shown to every user viewing the feed — they have no accept/reject lifecycle, no per-user selection, no independent reuse. The `angle` table's whole reason for existing is that a *specific user's specific composition* references *one specific chosen* angle row. Reusing it here would mean giving a global, unowned, never-selected string its own table row — that's exactly what principle 4.4 says not to do.
- No `discovery_source` child table for V1 — a single `sourceUrl`/`sourceName` pair on `discovery_item` is enough; only split it out if an item genuinely needs multiple sources later.
- `archivedAt` (nullable) soft-archives stale items out of the active feed without breaking `content.discovery_item_id` references from posts already created off them.

### 2.13 Consistency / Notifications

- **No separate `email_delivery` table.** Two columns directly on `notification` (`emailStatus`, `emailSentAt`) cover V1's fire-and-forget email side-channel at 10-user volume. Split this into its own table later if email retry/delivery-tracking logic grows — not worth it now.
- **Duplicate-reminder prevention lives on `notification_preference`**, not as a DB constraint (a "one reminder per inactivity streak" rule isn't cleanly expressible as a static unique index): `lastReminderSentAt` + `lastReminderForActivityAt` let the daily Trigger.dev job compare "has the user's last-published-at timestamp changed since we last reminded them" before creating a new notification row.
- `notification.type` enum currently has exactly one value (`consistency_reminder`) — kept as an enum (not a bare string) so future notification types are a deliberate, typed addition rather than a free-text drift.

## 3. Ownership Chains (no direct `user_id` unless justified)

Per Module 18's own rule, `user_id` is **only** added directly where it provides a real authorization/index/query benefit. Everything else is authorized by walking the chain.

| Table | Ownership path | Direct `user_id`? |
|---|---|---|
| `application_profile` | own PK = FK to `user` | Yes (it *is* the profile) |
| `social_connection` | → `user` | Yes (root-level resource) |
| `media` | → `user` | Yes (root-level resource, library semantics) |
| `content` | → `user` | Yes (root-level resource) |
| `angle` | → `content` or `research` → `user` | No |
| `composition` | → `content` → `user` | No |
| `draft` | → `composition` → `content` → `user` | No |
| `x_thread_post` | → `draft` → ... → `user` | No |
| `publication` | → `composition` → `content` → `user` | **Yes** — justified: primary dashboard queries are `(user_id, status)` and `(scheduled_for, status)`; joining through 3 tables for every list view is real overhead this table specifically earns an exception for. |
| `ai_generation` | → `draft` → ... → `user` | No |
| `research` | → `user` | Yes (root-level resource) |
| `discovery_item` | global, no owner | N/A |
| `user_discovery_item` | → `user` (composite PK) | Yes |
| `notification` | → `user` | Yes (root-level resource) |

**Rule enforced in application code, not just here:** never fetch `draft`, `composition`, `angle`, `ai_generation`, or `x_thread_post` by ID alone — always join up to verify the owning `user_id` matches the authenticated session.

## 4. Delete/Cascade Policy (final)

```text
user (Better Auth)
 ├─ application_profile        CASCADE
 ├─ social_connection          CASCADE
 ├─ media                      CASCADE
 ├─ content                    CASCADE
 ├─ research                   CASCADE
 ├─ notification               CASCADE
 ├─ notification_preference    CASCADE
 └─ publication (direct FK)    CASCADE   [only fires if content-tree cascade already permitted it]

content
 ├─ content_context_media      CASCADE
 ├─ angle                      CASCADE
 └─ composition                CASCADE
        └─ draft               CASCADE
               ├─ ai_generation        CASCADE
               ├─ x_thread_post        CASCADE
               └─ draft_media          CASCADE

composition ← publication.composition_id     RESTRICT   ★ blocks the whole cascade above
draft       ← publication.draft_id           SET NULL
social_connection ← publication.social_connection_id   SET NULL
x_thread_post ← ai_generation.target_x_thread_post_id  SET NULL
x_thread_post ← draft_media.x_thread_post_id           CASCADE
media ← content_context_media.media_id       RESTRICT
media ← draft_media.media_id                 RESTRICT
research ← content.research_id               SET NULL
research ← angle.research_id                 CASCADE
discovery_item ← content.discovery_item_id   SET NULL
draft ← draft.target_external_post_id → x_external_post   SET NULL
draft ← draft.target_publication_id → publication         SET NULL
```

**The ★ line is the whole safety mechanism from §2.4/§2.9**: because `publication.composition_id` is `RESTRICT`, a `DELETE FROM content WHERE id = ...` that would cascade down to a composition still carrying a live publication fails atomically — Postgres raises the FK violation and the entire statement rolls back. The application layer should catch this and surface: *"Can't delete — this has published or scheduled posts. Cancel schedules or delete the posts from [platform] first."*

## 7. Transaction Boundaries

| Operation | Atomic unit |
|---|---|
| Accept AI proposal | Update `draft.body_text` (or `x_thread_post.body_text`) + `ai_generation.status/resolved_at` + `draft.current_ai_generation_id` + `draft.pending_ai_generation_id = NULL` |
| Reject/Undo AI proposal | Update `ai_generation.status/resolved_at` + `draft.pending_ai_generation_id = NULL` (draft body untouched) |
| Restore AI generation | Insert new `ai_generation` (accepted) + update `draft.body_text` + `draft.current_ai_generation_id` |
| Schedule | Insert `publication` (status=scheduled, snapshot=...) + store `trigger_task_id` once Trigger.dev accepts the task |
| Update scheduled snapshot | Update `publication.snapshot` in place (same row — it's still "one schedule, one snapshot," just replaced on explicit confirmation) |
| External deletion | Update `publication.status='deleted'` + `deleted_at` (or `delete_failed` + `last_error`) |
| Social disconnect | Update `social_connection.status` / `disconnected_at` only. Publications react asynchronously at publish-time. |

## 8. What Deliberately Did Not Become a Table

- **Manual edit history** — explicitly not persisted (locked decision).
- **Content-journey/streak tracking** — posting history (`publication`) is the source of truth; no separate `streak` or `metrics` table, per Engineering Spec §22 ("avoid maintaining a second independent streak truth").
- **Discovery source as its own table** — a single URL/name pair suffices until a real multi-source need appears.
- **Email delivery log** — two columns on `notification` cover V1 volume.
